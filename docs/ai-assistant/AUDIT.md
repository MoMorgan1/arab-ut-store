## Confirmed strengths

- Every conversation read/write query is owner-scoped before public-ID lookup;
  React renders message content as text, so the reviewed path adds neither an
  IDOR nor an HTML injection sink.
- Guest identifiers in the chat ownership tables are keyed hashes, key
  rotation has continuity, and login claim preserves message/conversation IDs
  inside transactions. The separate raw-token session boundary is AI-B09.
- Pagination is bounded, cursor ownership is checked, no-store is applied to
  tested success/error paths, and disabling chat creates no session or database
  state.
- Optimistic sending stays available during rapid input, uses FIFO network
  dispatch, and retains one client ID across retry.
- Physical bubble placement is locale-independent while message content uses
  automatic direction; the 16px mobile composer font avoids iOS input zoom.

## P0/P1 release gate

| Severity | Open findings | Gate effect |
| -------- | ------------: | ----------- |
| P0       |             0 | None.       |
| P1       |             0 | None.       |

**Gate result: Proceed to Task 2.**

The `CreateChatMessage` check-then-insert path is explicitly **not** classified
as P1. The schema's `(conversation_id, client_message_id)` unique key prevents
two customer rows from committing, authorization has already selected an
owner-bound conversation, and the failed transaction cannot commit its demo
reply or timestamp update. The unhandled concurrent race can give one request a
transient failure after the other succeeds. Separately, after a lost successful
response, sequential retry returns the committed customer message but
`demoReply: null`, so an already-stored demo reply remains absent from the
current UI until history is reloaded. Both outcomes violate complete response
recovery, but neither violates confidentiality or persistent integrity. Under
this phase's binding severity rule, they are P2 reliability hardening (AI-B04),
not a release-stopping security/data-integrity repair.

Correcting the raw-token storage guarantee also does not change the P0/P1 gate.
The chat ownership tables remain HMAC-only, the token is generated from 32
random bytes, and no token exposure or cross-owner exploit was demonstrated.
The open fact is that Laravel session storage retains the raw token and the
production driver/encryption state was not inspected. Selecting and verifying
that confidentiality boundary is therefore P2 hardening/decision work
(AI-B09), not evidence of a current release-stopping compromise.

## Test interpretation

- Backend feature tests exercise the real Laravel routes, session/auth stack,
  SQLite schema, models, and database state. They do not create simultaneous
  requests or run MariaDB. The separate audited-head workflow did run the
  MariaDB fresh/rollback/migrate lifecycle, but did not directly query invalid
  chat owner rows.
- Frontend tests give useful contract evidence for isolated hooks/components
  and a persistent-root simulation. They do not mount the shipped application,
  execute a browser layout engine, or validate console/runtime asset behavior.
- Therefore the focused baseline supports the P0/P1 code gate but does not
  replace Task 2's browser smoke or later cross-engine verification.
