Q1 Three action labels, because they are three different writes. Send appears only on a row with no fulfillment job — it re-opens the order’s outbox row so the placement request goes out again. Resume and Retry appear only when the job’s own allowed_actions lists them, and they instruct a supplier about work it already holds. A row that already has a placement is never offered “Send” — that is the double-spend, and the defence is that the control does not exist, not that the server returns a 409. AUT-1036 shows a dash because its only allowed action is the customer’s, not ours.

§1.1 Supplier is read from the placement, not the job mirror — AUT-1039’s challenge phase can sit at a different supplier than the job column advertises.  ·  §3 AUT-1042 is an unplaced alarm: a paid item with no fulfillment job row at all. A jobs-only screen could not show it, and it is the one silence nothing else in the store reports.  ·  Q4 There is no Failed chip in the state filter. FulfillmentStatus::Failed is never assigned anywhere in the codebase, so it could never match a row.

The cost is withheld by the server, not hidden by the browser. The Query does not select actual_cost_halalah for a Staff actor and the Presenter never emits the key — not null, absent — so a Staff payload read in the network tab contains no trace of it. sort=actual_cost is removed from that actor’s allowlist and fails validation rather than falling back silently: a silent fallback is an oracle that tells the caller the column exists.

my call I made the re-send Admin-only, and you should overrule me if you disagree. Three reasons. It spends money, and permissions.md already draws the Admin/Staff line exactly there — Staff hold orders.cancel but not orders.refund, not payments.refund, not wallet.adjust. The actor cannot see what it costs, by your own Q5 answer, so they could not tell a 60-riyal re-send from a 600-riyal one. And pressing it decrypts the customer’s EA credentials (artboard 6). You expanded Staff to seeing the screen; reading that as also granting a spending action would be inventing a decision you did not make. The sidebar here also shows fewer sections, because Staff already hold none of the catalog, marketing or settings permissions.

forms.md:17-18 — "Destructive confirmations name the record and consequence. Buttons say the actual action, not ‘Yes’ or ‘Submit’." So the dialog names the order, says plainly that a supplier will be asked and we will be charged, and its button says Send to supplier.

The request carries the customer’s EA account, decrypted for this send only and written to the secret access log. You will be asked for your password.

Reason is a fixed list, not a text box. forms.md:37-41 requires an allowlisted reason code and audit-logging.md:14-16 forbids copying free-text reasons into audit metadata. Four codes cover what actually happens: never_placed, callback_lost, supplier_stalled, customer_report.

The credential line is not boilerplate. ComposePlacementRequest decrypts the customer’s EA account when the request is built and writes a SecretAccessLog row for each read. The operator never sees the credentials, but the press is what triggers the read — so the route carries EnsureAdminPassword, the same recent-password middleware already wrapping settings and MFA, and the dialog says so before the press rather than surprising them with a password prompt after it.

So the row says Queued, never Placed, and the Unplaced alarm stays on the row until the sweep sees a job appear. 8 · What is deliberately not on these artboards read this before approving

One of the plan’s six columns has no data behind it

The plan asks for supplier, age, stall, failure, actual cost and retry. Five are drawn above. Failure is listed here instead of being drawn empty, because a mock showing a column the store cannot fill is a promise the code will not keep. Full evidence with line numbers is in docs/design/e1-admin-fulfillment-screen.md.

Column What the plan implies What the code actually holds
failure A stored error per item. fulfillment_jobs.last_error and last_error_code are never written non-null — the only writers set them to null (RecordSupplierPlacement.php:227,242). The fulfillment_attempts table has a model, a relation and no writer anywhere. attempt_count is never incremented. FulfillmentStatus::Failed is never assigned in app, database or tests. Your Q3: leave it alone in this slice, so the Signal column carries what exists today — observed_state (the supplier’s own code, "carried for diagnosis only"), poll_failure_count, and the alarm. The read failure reason exists in memory and is discarded after the log line; persisting it is owed work for a later fulfillment slice.
retry One column, one action. Built (your Q1), but as three actions, not one. Send re-opens the order’s outbox row — it is the only one that spends new money, and it exists only where there is no job. Resume and Retry instruct a supplier about work it already holds, and appear only when the job’s allowed_actions lists them. A second order.paid event cannot even be created — its idempotency key is 'order-paid:'.$order->id and the column is unique — which is why the re-send re-opens the existing row rather than writing a new one, and why the request that goes out can only contain items that still have no job.
actual cost A number on every row, for everyone. Real writer, conditional data, and now Admin-only. actual_cost_halalah is written only when the supplier payload carries a cost and an applied pricing run carries ratioEuroUsd — "a cost we cannot convert is not a cost we should invent". With pricing runs currently failing, expect many nulls; artboards 1 and 5 show the null rendering as not reported and —, never SAR 0.00.
customer name — Left off on purpose. This screen answers "what is stuck", not "whose". The order number is a link and the customer is one click away. A name column widens every row for information the operator does not act on here.
manual alarm resolve — Your Q6: no. resolved_at is written only by the sweep, when the condition ends. An alarm a human can dismiss without the item changing is an alarm nobody trusts.
