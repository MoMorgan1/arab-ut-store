Slice E1 of docs/plans/2026-09-12-order-tracking-in-store.md (lines 997–1001). Every paid item a supplier still owes, inside the existing Admin, with its permission, its server-side filter and sort allowlists, and its staff audit. The findings note beside this file — docs/design/e1-admin-fulfillment-screen.md — carries the evidence for every claim below, with file paths and line numbers.

This canvas shows only columns the database can fill. The plan names six things — supplier, age, stall, failure, actual cost, retry. Four have writers. Failure and retry, as the plan words them, do not: see the last panel on this page. A mock showing a column the store cannot fill is worse than one that omits it, so those two are absent here, deliberately, and the panel says why.

Nothing has been built. This is the UI gate in CLAUDE.md: inspect, canvas, approve, then code. Six questions need your answer before E1 is implementable — they are numbered Q1–Q6 in the findings note, and the ones this canvas can show are marked on the artboards.

Q1 The gold button is disabled and that is the question. The plan promised the admin's own resume button — "the customer's button on the card, and the admin's when the admin surface exists" (2026-09-12-order-tracking-in-store.md:1032-1035). No admin route, permission or audit event for it exists today, and pressing it would spend money at a supplier and change what a customer sees, so it is yours to decide. Read-only E1 ships sooner; the control is drawn here so "yes" does not cost a second canvas.  ·  Q6 There is no "mark resolved" control. fulfillment_alarms.resolved_at is written only by the sweep when the condition actually ends, so an item you fixed outside the store stays listed until the sweep agrees. A manual resolve is a write that can lie, and it needs an audit event.

5 · What is deliberately not on these artboards read this before approving

Two of the plan's six columns have no data behind them

The plan asks for supplier, age, stall, failure, actual cost and retry. Four are drawn above. The other two are listed here instead of being drawn empty, because a mock showing a column the store cannot fill is a promise the code will not keep. Full evidence with line numbers is in docs/design/e1-admin-fulfillment-screen.md.

Column What the plan implies What the code actually holds
failure A stored error per item. fulfillment_jobs.last_error and last_error_code are never written non-null — the only writers set them to null (RecordSupplierPlacement.php:227,242). The fulfillment_attempts table has a model, a relation and no writer anywhere. attempt_count is never incremented. FulfillmentStatus::Failed is never assigned in app, database or tests — a "Failed" filter would return zero rows forever. What exists instead is the Signal column drawn above: observed_state (the supplier's own code, "carried for diagnosis only"), poll_failure_count, and the alarm. The read-failure reason lives only in memory and the log.
retry An operator retry, with a count. ResumeItemDelivery and RetryItemChallenge are customer actions — their only routes are storefront routes, and both fail closed unless the job's own allowed_actions lists the action. challenge_retries is not an operator log: it counts the automatic challenge retry, per challenge id. There is no admin route, no permission and no audit event. See Q1.
actual cost A number on every row. Real writer, conditional data. actual_cost_halalah is written only when the supplier payload carries a cost and an applied pricing run carries ratioEuroUsd — "a cost we cannot convert is not a cost we should invent". With pricing runs currently failing, expect many nulls. Rows 5 and 4 above show the null rendering: not reported and —, never SAR 0.00.
customer name — Left off on purpose. This screen answers "what is stuck", not "whose". The order number is a link, and the customer is one click away on the order. Adding a name column widens every row for information the operator does not act on here.
